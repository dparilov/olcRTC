# v2 Spec — Parallel Branch / Parallel Deploy, Yandex-SSO-First Tenant Model

## Status

This spec defines a **new architecture branch**.
It does **not** replace the current working deployment in-place.

This work must be implemented:

- in a separate git branch
- with a separate server deployment
- with a separate external API endpoint / port
- without breaking the current production-like setup

The current working deployment remains the stable baseline while v2 is built and validated in parallel.

---

# 1. Goal

Build a new tenant/session architecture where:

- Yandex SSO becomes the primary user identity
- internal tenant remains as a server-side object
- secret is no longer user-facing
- secret is generated automatically at tenant registration
- secret is stored securely and hidden from the user
- UI is simplified
- watcher becomes shared
- stale per-tenant runtime processes are eliminated
- the whole solution is developed and deployed in parallel to the current branch

---

# 2. Hard boundary

This is a **separate architecture track**.

It must not:
- break the current deployment
- mutate the current stable branch in-place
- require risky migration before validation
- force immediate replacement of the current model

This v2 work is intentionally isolated.

---

# 3. Deployment model

## 3.1 Separate branch
Implementation happens in a dedicated new branch.

## 3.2 Separate server deployment
The v2 server must be deployed separately from the current one.

### Required
- separate API endpoint and/or port
- separate process/service name
- separate state directory / storage
- separate logs
- separate config
- ideally separate OAuth app credentials too, if practical

## 3.3 No production replacement yet
The current deployment remains untouched until:
- v2 is functionally complete
- v2 passes E2E
- v2 is explicitly accepted

---

# 4. Identity model

## 4.1 Primary identity = Yandex SSO
User identity is based on Yandex login / OAuth / SSO.

## 4.2 Internal tenant remains
Internal tenant is still kept as a server-side object.

### Why
It is still useful for:
- routing
- ownership
- storage namespace
- policy
- future migration to other IdPs
- internal server abstraction

## 4.3 One user -> one tenant in v2
For the first version of this model:
- one Yandex user maps to one internal tenant

This may be generalized later if needed.

---

# 5. Secret model

## 5.1 Secret is removed from user-facing settings
The user must not enter or manage a manual secret in UI.

## 5.2 Secret is autogenerated
At tenant registration time:
- the server generates a strong tenant secret
or
- the system generates it deterministically/safely in the registration flow

## 5.3 Secret is hidden from the user
The secret is not displayed in normal UI.

## 5.4 Secret storage
The secret must be:
- securely stored on the client
- securely stored on the server if needed for verification/runtime
- not exposed in normal user flows

## 5.5 Manual secret editing is removed
There is no normal user flow for editing/changing the secret.

---

# 6. UI model

## 6.1 Settings must be simplified
Normal settings should contain only:
- `Endpoint`

Nothing else should be required in normal user flow.

## 6.2 Main action button
The main onboarding action becomes:

- `Login to Yandex / Create Tenant`

This single action is responsible for:
- login/authorization
- tenant creation/provisioning
- enabling the fallback capability
- obtaining required credentials/cookies/tokens

## 6.3 Token handling is hidden
The OAuth token itself must not be shown in normal UI.

## 6.4 Hidden maintenance menu
A hidden maintenance/debug menu is allowed.

### Access
- hidden behind repeated tapping on app version

### Purpose
- manual token refresh
- manual token upload
- break-glass maintenance path if automated token handling fails or token expires

This path is intentionally non-primary.

---

# 7. Registration flow

## Normal user flow
1. user enters or already has endpoint
2. user presses `Login to Yandex / Create Tenant`
3. app performs Yandex auth flow
4. server provisions internal tenant for that user
5. server stores or enables fallback credentials
6. client stores returned identity/runtime state
7. user continues with room/session usage

### Important
The user should not need to:
- enter secret
- manually upload token
- understand tenant internals

---

# 8. OAuth / cookie flow

## 8.1 Preferred path
The normal path should be integrated:
- Yandex login
- consent
- token acquisition
- capability enablement

## 8.2 Hidden fallback path
If token handling breaks:
- user may go to hidden maintenance menu
- manually refresh or upload token

## 8.3 UX principle
Manual token management is a maintenance path, not the primary product path.

---

# 9. Watcher model

## 9.1 Shared watcher service
The watcher must become shared.

The system should no longer create per-tenant pending watcher processes.

## 9.2 Watcher activation
A tenant/user folder begins to be watched after:
- successful registration / login
- token availability
- fallback enabled for that tenant

## 9.3 Why this helps
This removes one major resource problem:
- no explosion of stale per-tenant always-on watcher processes

---

# 10. Important clarification on stale resource handling

## Yes, shared watcher solves one class of stale-resource problem
It helps with:
- stale tenant watcher processes
- unnecessary per-tenant always-on processes
- duplicated “listening” resources

## But it does NOT eliminate all stale-resource problems
Stale **sessions** can still exist.

Therefore v2 still needs:
- session lifecycle cleanup
- session timeout policy
- abandoned runtime cleanup
- stale session GC

So:

- shared watcher solves stale **tenant-watcher** waste
- but not stale **session** waste

---

# 11. Session/resource model

## 11.1 Dynamic session allocation
Ports/resources should be allocated per session rather than permanently baked into tenant behavior when possible.

## 11.2 Internal tenant remains stable
Tenant remains:
- identity / ownership / policy / namespace

## 11.3 Session is ephemeral
Session owns:
- current room
- runtime state
- allocated ports/resources
- current connection lifecycle

This is cleaner than making tenant itself the runtime object.

---

# 12. Client contract

## Normal visible client settings
- Endpoint only

## Internal client state may include
- tenant id
- session info
- hidden generated secret
- token state
- capability flags

But these are internal implementation details, not primary user-facing settings.

# 13A. Bootstrap endpoint availability

## Accepted weak point
In this phase, the bootstrap endpoint is the single weak point of onboarding.

### Truth
- initial registration requires bootstrap endpoint availability
- if bootstrap endpoint is unavailable, onboarding is deferred
- this phase does not introduce a separate fallback for initial registration
- this is an accepted limitation for v2 Phase 1.5

### Implication
After successful registration/login, the system becomes much more resilient.
Before that point, bootstrap endpoint availability is mandatory.

---

# 13B. Multi-device policy

## Identity split
The model is explicitly:

- one Yandex user = one tenant
- one tenant may have multiple devices
- each device has its own stable `device_id`
- sessions are separate from devices and tenants

## Device model
Each app installation must generate and persist its own `device_id`.

The server uses `device_id` to distinguish:
- same user, different device
- last seen device
- active device/session ownership

## Session policy
For this phase, the system allows:

- multiple devices per tenant
- **only one active server-side session per tenant at a time**

### Rule
If a new session is started for the same tenant:
- the new session becomes authoritative
- the old active session is terminated/replaced

This is the chosen simplicity-first policy for the first version.

## UX implication
A second device may:
- connect to the current session
- or create a new session, which kills the old one

Takeover semantics should be clear in logs/status, but the server-side rule is:

> newest session wins

# 14. Recommended implementation order

1. create separate branch
2. create separate bootstrap/server deploy
3. switch identity model to Yandex SSO-first
4. keep internal tenant object
5. remove user-facing secret field
6. implement autogenerated hidden secret
7. simplify settings UI to endpoint only
8. add `Login to Yandex / Create Tenant`
9. implement hidden maintenance menu for token recovery
10. introduce shared watcher service
11. introduce session-based resource allocation/cleanup
12. run isolated E2E against the new deployment

---

# 15. Acceptance criteria

This v2 track is accepted when:

1. it runs on a separate branch and separate deployment
2. it does not break current stable deployment
3. user-facing settings contain only endpoint
4. normal flow uses `Login to Yandex / Create Tenant`
5. secret is autogenerated and hidden from user
6. OAuth/token management is integrated into the normal login flow
7. manual token upload exists only in hidden maintenance flow
8. shared watcher is used instead of per-tenant watcher processes
9. stale tenant watcher-process problem is eliminated
10. session cleanup strategy exists for stale runtime/session resources
11. bootstrap endpoint availability as onboarding dependency is explicitly accepted in docs
12. multi-device policy is explicitly defined:
    - one user = one tenant
    - multiple devices allowed
    - one active session per tenant
    - new session kills old session
13. the new architecture passes isolated E2E before any migration discussion

---

# 16. Non-goals

This v2 track does NOT include:
- transport refactor
- peer/mux changes
- VPN transport redesign
- immediate migration of the current deployment
- removal of internal tenant concept
- exposing advanced token/secret controls to normal users

---

# 17. Final summary

This v2 direction should be understood as:

- separate branch
- separate deployment
- Yandex SSO as primary identity
- internal tenant retained
- user-facing secret removed
- secret autogenerated and hidden
- endpoint-only settings
- integrated login/create-tenant flow
- hidden maintenance path for token recovery
- shared watcher
- session-centric cleanup of runtime resources

This allows the new architecture to be developed safely in parallel without destabilizing the current working system.

# 19. Resolved questions

1. **OAuth client_id** — same as v1 (`466e5098b9254404a57bb50af62a5160`). No change needed.
2. **Telemost room lifecycle** — unchanged from v1. Same room creation/join flow.
3. **Port pool size** — 100 concurrent sessions. Pool range: ports 2080-2179 (SOCKS) + 3080-3179 (API).
4. **Watcher mechanism** — same polling approach as v1. No webhook API available.
5. **Monitoring** — deferred. Not in v2 Phase 1.
6. **Rate limiting** — enabled. Per-tenant session creation: max 1 session/minute. Exceeding returns 429 with `Retry-After` header. User-facing: "Please wait before creating a new session." Reasonable wait is acceptable UX trade-off.
# v2 Spec Addendum — Tightening Clauses Before Coding

## Purpose

This addendum does not change the approved v2 direction.

It exists only to remove remaining ambiguity before implementation.

The architecture remains:

- separate branch
- separate deployment
- Yandex SSO as primary identity
- internal tenant retained
- hidden autogenerated secret
- endpoint-only settings
- hidden maintenance token path
- shared watcher
- one active session per tenant
- new session kills old one

This addendum makes key runtime and lifecycle rules explicit.

---

# 1. Generated secret lifecycle

## Rule
The tenant secret is generated once during first successful tenant provisioning.

## Required
- the secret is not shown to the user
- the secret is not editable in normal UI
- the secret is not exportable through normal UI
- the user does not manually rotate the secret in v2

## Explicit product truth
There is no user-facing secret management feature in this phase.

If secret replacement is ever needed later, it is a separate server-side migration/maintenance feature, not part of normal user flows.

---

# 2. Device model is mandatory

## Rule
Every installation of the client application must generate and persist its own `device_id`.

## Required properties
- created once on install / first run
- stored securely and persistently on the device
- sent to the server after login / tenant binding
- used as the stable identity of that device installation

## Purpose
`device_id` is required for:
- multi-device handling
- session ownership
- takeover semantics
- observability
- conflict-free same-user login from multiple devices

This is not optional.

---

# 3. Session creation / takeover semantics

## Rule
A **new session** is any server-side session start request for the same tenant that is intended to become the active session.

## In this phase
When a new session is accepted for the same tenant:
- the new session becomes authoritative
- the old active session is terminated/replaced

## Explicit server-side truth
`new session kills old session`

This is the chosen simplicity-first policy.

## Required
The implementation must not leave takeover semantics implicit.

The code should make it clear:
- which action creates a new session
- which action only attaches to existing session
- which action is a takeover

---

# 4. Shared watcher scope

## Rule
The shared watcher does NOT watch every registered tenant automatically.

## Required
The shared watcher watches only tenants/users for whom fallback capability is enabled.

### In practice
A watcher is active only after:
- tenant/user identity exists
- token/capability is available
- fallback is enabled

## Purpose
This prevents unnecessary resource usage and avoids stale always-on watcher behavior.

---

# 5. Bootstrap endpoint availability is an accepted limitation

## Rule
Bootstrap endpoint availability is the single accepted weak point of initial onboarding in this phase.

## Explicit truth
If bootstrap endpoint is unavailable:
- first registration/login cannot complete
- no onboarding fallback is provided in this phase
- this is accepted by design

## Required
This must be documented clearly so implementation does not try to invent hidden fallback behavior.

---

# 6. Session cleanup must be explicit

## Rule
When a session is terminated or replaced, cleanup must be explicit.

## Required cleanup
- old session marked terminated
- runtime resources released
- watcher/session references cleaned if applicable
- per-session ports/resources released if session-scoped
- stale session state not kept as active

## Purpose
The “new session kills old one” rule is incomplete without explicit cleanup semantics.

---

# 7. Hidden maintenance path scope

## Rule
The hidden version-tap menu is strictly a maintenance path.

## Allowed uses
- manual token refresh
- manual token upload
- operational diagnostics if explicitly needed

## Not allowed
- normal onboarding
- normal login
- normal secret management
- regular day-to-day user actions

This prevents hidden debug UX from leaking into the main product path.

---

# 8. Coding readiness verdict

With this addendum applied, the v2 specification should be treated as:

**coding-ready**

No more conceptual questions should be solved by the coding agent itself.
